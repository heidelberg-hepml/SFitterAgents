# `/sf-datacard`

The datacard-assembly workflow — the phased sequence for turning the upstream artifacts into the SFitter JSON entry (one observation + one prediction, paired by `ID`) and validating it to a hard gate. The orchestration disciplines it leans on are always-loaded, not restated here: dual-spec, regime classification, slice-boundary premises, reconcile-by-re-engaging, and revise-before-caveat live in `lead-discipline.md`; "a clean run is not evidence" — here, *a file that is well-formed JSON is not a file that `ReadDataCard` accepts, and one `ReadDataCard` accepts is not one whose conventions are right* — lives in `rules/ma-outcome-not-evidence.md`. This skill is the assembly-specific scaffold over them.

This is the assembly stage of the `sf-reinterpret` family. It is **downstream of three siblings and consumes their reviewer-approved outputs**: the structured extraction report from `sf-extract` (observation values, per-bin per-source modifier arrays, canonical names), the SM template + theory budget from `sf-sm-template` (prediction `data` at the right perturbative order, `ScaleSim`/`PDFSim` magnitudes), and the κ/D6 tables from `sf-parameterize` (the linear/quadratic/interference contributions). `sf-deep-verify` is the deeper-verification sibling on the user's ask. **Compute is N/A inside this skill** — assembly and validation are file work and a local `ReadDataCard` round-trip, all local. Running the actual SFitter fit is a **GPU job and the lead's job via `cluster-submission`**, not part of this assembly skill (Phase 6).

The dual-spec discipline maps directly: the **physics-spec** is what the measurement *is* (the observable, process, √s, experiment, the operators parameterized) as carried in the upstream reports; the **datacard-spec** is what the assembled JSON actually encodes (the modifier `type`s it assigns, whether a value sits in a `%` or absolute slot, the `ID` string the fields decode to, the array lengths the entry actually has). The two silently diverge exactly where the assembly breaks — a theory magnitude dropped into a `syst` slot instead of `theo`, an absolute κ contribution written where a percentage is expected, an `ID` whose decoded experiment digit disagrees with the `name`. Build every slot on what its owning agent says it must carry — the schema for structure, the catalog for the name/label, the ID encoding for the encoded string — read in both directions: a modifier the measurement needs can be silently absent (a required `Pois`/`stat`/`Luminosity` never lifted from the report), and one you never intended silently present (a luminosity modifier surviving into a normalized-ratio observation where `sf-extract` already cancelled it).

---

**Phase 1 — Frame: confirm the inputs are ready.** Assembly is a lift, not a re-derivation — its quality is bounded by the artifacts it consumes, so confirm all three are present and reviewer-approved before placing a single slot. Required inputs: (a) the **reviewed extraction report** from `sf-extract` (canonical-named modifiers with per-bin `values_percent`, central values, bin edges, the absolute-vs-normalized / fiducial-vs-total classification — only reviewer-APPROVED values proceed); (b) the **SM template + theory budget** from `sf-sm-template` (per-bin $\sigma_{{\rm SM},b}$ at the correct perturbative order, with the `ScaleSim`/`PDFSim` template uncertainties and any applied k-factor); (c) the **κ/D6 tables** from `sf-parameterize` (per-bin $\kappa_{1}$/$\kappa_{2}$ per operator and any interference, with fit quality). Capture the physics-spec verbatim per dual-spec. If any upstream artifact is missing or un-reviewed, **surface and stop** — do not back-fill a value yourself; route to the owning sibling skill. The observable's regime (single-bin total xsec vs differential; normalized vs absolute) routes the field choices in Phases 2–3.

**Phase 2 — Assemble the observation.** Place each extracted source into its `modifiers[]` slot per the schema (this skill + `docs/sfitter/01_json_schema.md`): the observation object nests `Meas`/`Bkg` (`{data, modifiers}`) — measured values in `Meas.data`, background in `Bkg.data`, no flat observation `data`; `pois`/`stat`/`syst` modifiers sit under `Meas`/`Bkg` and `theo` at observation level; and **observation modifier values are PERCENTAGES** of the measured value (`pois` the exception, typically `0.0` for unfolded). Dispatch two agents in one round for the pieces the schema doesn't fix:
- `sf-modifier-namer` — confirm each `name` is the canonical catalog name and each `label` the correct correlation group (`LHC` for luminosity, `ATLAS`/`CMS` experiment-specific, `Theo`, `Stat`, `Pois`). The extraction report should already carry canonical names; if one does not match the catalog, that is a re-extraction (re-engage `sf-extract`), not a rename here.
- `sf-id-encoder` — construct the 7-char `ocfkkxe[_b]` `ID` from the measurement metadata, run its round-trip decode, and confirm name–ID consistency.

The schema/parse validation of the assembled result is Phase 5 (`sf-datacard-schema-reviewer`); assemble here, validate there.

The hard structural invariant: **every modifier `data` array has the same length as `Meas.data` and as `bin_widths`** (use `[1.0]` bin_widths and a `_0` bin suffix for a single-bin total xsec). `Meas.data` is the measured central value per bin from the extraction report; `Bkg.data` is the background. There is no flat observation-level `data` — a card carrying one fails `ReadDataCard` with `KeyError: 'Meas'`.

**Phase 3 — Assemble the prediction.** Same `name` and the **same `ID`** as the observation (the pairing key — re-confirm via `sf-id-encoder` if reconstructed). `data` is the per-bin SM prediction $\sigma_{{\rm SM},b}$ from `sf-sm-template`. The Wilson-coefficient modifiers are the D6 contributions from `sf-parameterize`, and their **value convention is ABSOLUTE, not κ**: ${\rm lin}_{i,b}=\kappa_{1,i,b}\,\sigma_{{\rm SM},b}$, ${\rm quad}_{i,b}=\kappa_{2,i,b}\,\sigma_{{\rm SM},b}$, named bare `D6{op}` (linear), `D6{op}xD6{op}` (quadratic), and `D6{op1}xD6{op2}` (cross/pairs) — NO `_lin`/`_quad`/`_interf` suffixes (preserve casing — the names are lower case, `D6qu1`, never `D6Qu1`). Each operator that appears should carry both its bare-name linear and its `D6{op}xD6{op}` quadratic; the linear term may be negative. The D6 slot shape is in this skill and `docs/sfitter/03_predictions_format.md` (the schema-reviewer validates it in Phase 5); the numbers themselves come from `sf-parameterize`, not authored here. Same array-length invariant: every prediction modifier `data` array equals the prediction `data` length.

**Phase 4 — Methodology choices.** Dispatch `sf-methodology-consultant` for the run-side knobs the datacard or its accompanying fit config must carry, as relevant to this measurement: the **fitter** (flow / smc / craft), the **likelihood** (profile / toy / spiral / five_point — `profile` requires the datacard path), the **precision** (single / double), and the **RFit-flat-vs-Gaussian** treatment that the modifier `type`/`label` choices imply (theory `theo` modifiers are RFit-flat; systematics are Gaussian; the $\rho=0.99$ within-experiment correlation). This confirms the Phase-2/3 `type`/`label` choices are consistent with how the likelihood will actually treat each modifier — a cross-slice check between the schema slot and the fit framework. Magnitudes stay theory's, κ values stay parameterization's; this consultant owns only the framework treatment.

**Phase 5 — Validate (HARD GATE).** Two gates must both clear before Phase 6:
- **Schema/parse** — dispatch `sf-datacard-schema-reviewer`. Its definitive check is that the file loads end-to-end with SFitter's `ReadDataCard` (a local round-trip); the schema invariants (`Meas`/`Bkg` nesting, array-length equality, modifier type placement, percentage-vs-absolute conventions, ID pairing + validity + name-consistency, bare-`D6` prediction naming, required modifiers) are necessary but not sufficient — the parse round-trip is the gate, **not eyeballed**.
- **Documentation/adoption** — dispatch `sf-reviewer` for its documentation-completeness concern: `/output/documentation/datacard/` present, current, and adoption-gate-clean (every kept value traces to a saved, re-runnable script). This is the hard-gate concern the datacard deliverable carries; the schema-reviewer does not check it.

Each returns APPROVED / NEEDS REVISION / WARNING; **only when both APPROVE does the entry proceed to Phase 6.** Per reconcile-by-re-engaging, a NEEDS REVISION is not a caveat to ship around — re-engage the owning agent (the catalog for a name, `sf-id-encoder` for an ID, the upstream sibling for a value problem, or `sf-document` for a documentation gap) with the finding as an explicit premise, fix, and re-review.

**Phase 6 — Deliver.** Emit the validated JSON entry to `/output` (wrapped, or ready to concatenate, in the top-level `{"observations": [...], "predictions": [...]}` — an optional `"version"` may be added; it is not required). State explicitly what was assembled, the decoded `ID`, the operators carried, and any WARNING the reviewer left standing. **Running the SFitter fit is out of scope here** — it is a GPU job the lead submits via `cluster-submission` (the playbook), not a step of this assembly skill. Hand the validated datacard path to that flow when the user asks for the fit.

## Gates and validation checks (name them; do not eyeball them)

Before the entry is signed off, these must hold — confirmed by the owning agents (Phase 2/3) and the `ReadDataCard` round-trip (Phase 5), not by lead inspection:

- **Schema present** — top-level `observations`, `predictions` (`version` optional); each observation has `name`/`ID`/`bin_widths`, nested `Meas` and `Bkg` (each `{data, modifiers}`), and an observation-level `modifiers` (the theo list); each prediction has `name`/`ID`/`data`/`modifiers`. A flat observation `data` with no `Meas`/`Bkg` is invalid.
- **Equal array lengths** — within an observation, every modifier `data` length equals the `Meas.data` length and `bin_widths` length; within a prediction, every modifier `data` length equals the prediction `data` length. **Mismatched lengths are the #1 cause of `ReadDataCard` failure once the card loads.**
- **ID match** — the observation and its prediction share exactly one `ID`; no orphan on either side, no duplicate within an array.
- **ID validity + name consistency** — base is 7 digits (+ optional `_b`), fields in range, `f`/`kk` valid for the channel `c`, and the decoded ID agrees with `name` (e.g. name says ATLAS ⇒ `x=2`); bin suffix consistent with single-vs-multi-bin. Spec-vs-real deviations (`c=9` for $t\bar t\gamma$, `e=4` for 13.6 TeV) WARN, not REJECT.
- **Value conventions** — observation modifiers are PERCENTAGES (≥ 0, typically < 100; > 100 usually flags an absolute-mis-encoded-as-percentage error); prediction D6 modifiers are ABSOLUTE contributions, not κ. At least one `pois` and one `stat` modifier present.
- **Naming** — observation modifier `name`/`label` from the canonical catalog; prediction modifier names are bare `D6{op}` (linear) / `D6{op}xD6{op}` (quadratic) / `D6{op1}xD6{op2}` (cross), with NO `_lin`/`_quad`/`_interf` suffixes, correct casing.
- **Finite, positive `data`** — no NaN/Inf; observation and prediction `data` positive (cross-sections); single-bin total xsec ⇒ `bin_widths == [1.0]`.
- **`ReadDataCard` loads** — the file parses end-to-end with SFitter's `ReadDataCard` and every sub-id's `poiss_unc`/`stat_unc`/`syst_unc`/`theo_unc` resolves.

Failing any of these is a HARD STOP — fix before delivering, do not flag and proceed.

## Failure modes worth watching

- **Array-length mismatch** — a modifier with one fewer/more bin than `data`/`bin_widths`; the most common `ReadDataCard` failure. Re-check every array against the bin count.
- **Percentage-vs-absolute swap** — an absolute uncertainty dropped into a `stat`/`syst`/`theo` slot (which expect %), or a κ written into a D6 slot (which expects the absolute contribution $\kappa\,\sigma_{\rm SM}$). A factor-of-100 fit residual is the tell; > 100% modifier values flag it at validation.
- **ID/name disagreement** — a hand-built `ID` whose decoded experiment/energy/channel contradicts the `name`; or observation and prediction IDs that do not match, breaking pairing.
- **Missing always-required modifier** — no `Pois` (should be `0.0` for unfolded), no `stat`, or a `Luminosity` that the normalized classification says should have cancelled but is still present.
- **Non-canonical / mis-cased name** — a modifier name not in the catalog, or `D6Qu1` for `D6qu1`; resolve at extraction time (the modifier-namer), never silently rename at the datacard.
- **Authoring a value another agent owns** — back-filling a missing κ, SM `data`, or modifier magnitude in the assembly instead of routing to the owning upstream sibling. Assembly lifts approved values; it does not produce them.

## Document (hard gate)

The datacard is not shippable until `/output/documentation/datacard/` is current per `rules/sf-documentation.md` and the `sf-document` skill — this is part of the Phase 5 hard gate (enforced by `sf-reviewer`'s documentation concern), alongside the schema-reviewer's `ReadDataCard` round-trip. The bucket carries: the shipped `datacard.json` copied in; the `ReadDataCard` load log in `validation/`; and `datacard.md` logging the assembly choices (modifier→canonical-name mapping, theory-band sizing, ID encoding), each with its reasoning. Do not declare the datacard done without it.
