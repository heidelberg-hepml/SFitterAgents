# `/sf-extract`

The measurement-extraction workflow — the phased sequence for turning a measurement into a structured extraction report the datacard can consume. The orchestration disciplines it leans on are always-loaded, not restated here: dual-spec, regime classification, slice-boundary premises, reconcile-by-re-engaging, and revise-before-caveat live in `lead-discipline.md`; "a clean run is not evidence" — here, *a report that parses is not a report that is traceable* — lives in `rules/ma-outcome-not-evidence.md`. This skill is the extraction-specific scaffold over them.

This is the first stage of the `sf-reinterpret` family; the reviewer-approved report it produces feeds `sf-sm-template` (which builds the SM prediction at the right order) and `sf-datacard` (which assembles the SFitter observation from the extracted modifiers). Siblings `sf-parameterize` and `sf-deep-verify` are downstream. **Compute is N/A here** — extraction is reading (HEPData fetches, paper tables, figure digitization), all local; nothing in this workflow goes to the cluster, so `cluster-submission` does not apply until `sf-sm-template`/`sf-parameterize`.

The dual-spec discipline maps directly: the **physics-spec** is what the user described (which observable, what process, what the measurement *is*); the **extraction-spec** is what the retrieved artifacts actually carry (the bin edges HEPData lists, the source rows the paper's table actually has, whether the figure band is data-only or data+theory). The two silently diverge exactly where the extraction breaks — a "normalized" measurement whose table is actually absolute, a "total systematic" column that excludes theory, a source the paper folds into "Other". Build every value on what the artifact carries, read by its owning agent, in both directions: a source the measurement needs can be silently absent (a per-bin breakdown HEPData never published), and one you never intended silently present (a luminosity uncertainty in a normalized ratio where it should cancel).

---

**Step 1 — Frame the observable (REQUIRED first).** A single paper routinely carries several observables (inclusive, $m_{t\bar t}$, $p_T(t_h)$, $|y_t|$, …); extracting the wrong one is a total loss. Confirm with the user **which observable(s)** are being parameterized before any retrieval — do not assume. Capture the metadata *intent* (process, $\sqrt s$, luminosity, the reference, and the user's stated absolute-vs-normalized / fiducial-vs-total expectation) into the physics-spec, verbatim per the dual-spec discipline. If too vague to act, surface and ask. Regime-classification applies: the observable's regime (inclusive vs differential, tail-heavy vs central, normalized vs absolute) routes which agents Steps 2–4 implicate.

**Step 2 — Retrieve and classify.** Dispatch `sf-measurement-extractor` to walk the source hierarchy — **HEPData record first**, then paper main tables, then supplementary/auxiliary tables, then figures only as a last resort — returning per-bin central values, bin edges/widths, and the required metadata (process, observable, $\sqrt s$, luminosity, reference, HEPData record ID), **and** to classify WHAT was retrieved: **absolute vs normalized** and **fiducial vs total phase space**, with its self-consistency checks (inclusive-sum-to-$\sigma_{\rm tot}$ vs integrates-to-1, luminosity-present vs cancelled). Tables always beat figures on precision; HEPData beats the paper's main-text numbers when both report the same quantity. The classification is a gate, not a footnote — it decides which uncertainty sources cancel (luminosity drops out of a normalized ratio) and how the SM template must be treated downstream (per-bin k-factor for normalized differentials, an extrapolation modifier for full-phase-space). It is the cross-slice invariant this workflow most often gets wrong; the extractor determines it from the same artifacts it retrieved, in one pass.

**Step 3 — Name canonically.** Dispatch `sf-modifier-namer` to map the paper's uncertainty terms onto the canonical SFitter modifier names — "JES"+"JER" → `Jets`, "Electron ID"+"Muon ID" → `Leptons`, "ISR"/"FSR" → `partonShower` vs separate `ISR`+`FSR` vs `PSscale`, per-process background rows → the canonical `Bkg<Process>` entry — returning each source's correlation `label` and the extraction-priority tiers (always-required `Pois`/`stat`/`Luminosity`; high; medium; lower) as the shopping list. **Naming comes before decomposition** because the next step groups sources by canonical name: the namer decides which paper terms fold into one modifier; Step 4 computes the numbers under that grouping. A name resolved here keeps `sf-datacard` dumb (it consumes names, it does not decide them); a modifier-name mismatch surfaced at datacard time is a re-extraction, not a rename.

**Step 4 — Decompose uncertainties.** Dispatch `sf-systematics-decomposer` to produce the per-bin per-source uncertainty arrays **under the canonical names and groupings from Step 3**. The common case is the **Schmal two-step**: the paper exposes only a total-cross-section source breakdown and HEPData only per-bin totals, so it distributes via $\omega_b = \Delta_{{\rm tot},b}/\sqrt{\sum_j \Delta_j^2}$, preserving relative composition and matching the HEPData per-bin total by construction — quadrature-combining the sources the namer grouped under one name (√(JES²+JER²) → `Jets`). Have it return the round-trip checks (per-bin quadrature equals HEPData total; normalization $S$ equals the paper's quoted total systematic) and flag the edge cases it owns — tail bins where the inclusive composition under-represents jet/b-tag growth, canceling sources in normalized ratios, asymmetric $\pm$ systematics. When a needed source lives **only in a figure** (no table or HEPData equivalent), dispatch `sf-measurement-extractor` — it decides digitize-vs-hand-off, runs the calibration cross-checks, and flags the result `medium` with a specific figure pointer. Skip digitization whenever the same value is in any table.

**Step 5 — Review.** Dispatch `sf-reviewer` (the reinterpretation-layer reviewer — the sf-layer analog of the `mg-*` layer-reviewers) for a verdict. Its reinterpretation-specific concerns here: **extraction traceability** (every value points at a specific authoritative source), **decomposition integrity** (the Schmal round-trip closes; no source missing from $S$), and **normalization classification consistency** (the absolute/normalized and fiducial/total flags match what the retrieved artifacts actually do). It returns APPROVED / NEEDS REVISION / WARNING per modifier; **only reviewer-approved values proceed** to Step 6 and onward to `sf-datacard`. Per the reconcile-by-re-engaging discipline, a NEEDS REVISION is not a caveat to ship around — re-engage the owning agent (Step 2/3/4) with the reviewer's finding as an explicit premise, fix, and re-review.

**Step 6 — Produce the extraction report.** Emit the structured JSON report per `docs/measurement_extraction/04_extraction_report.md`: `measurement` metadata block, `bins[]` (central values + per-bin totals for cross-checks), `modifiers[]` (canonical name, `type`, per-bin `values_percent`, a **specific** `source` pointer, `confidence`, and `notes`), `uncertainty_ordering`, `correlation_matrix`. Each modifier carries a per-source pointer and a confidence label — `high` (direct table/HEPData), `medium` (Schmal-derived or figure-digitized with documented cross-check), `low` (estimated; reviewer-rejected by default). This report is the extraction-spec of record; it is what feeds `sf-datacard`.

## Gates and validation checks (name them; do not eyeball them)

Before the report is signed off, these must hold — they are the cross-slice invariants the assembled extraction implies, confirmed by the owning agents (Step 2 / Step 4 / Step 5), not by lead inspection:

- **Quadrature total** — per bin, $\sqrt{\sum_j \Delta_{b,j}^2}$ across systematic modifiers equals the HEPData per-bin `syst_unc_total` within ~1%. A larger gap means a missing source or a quadrature error.
- **Inclusive sum** — $\sum_b \sigma_b\cdot{\rm bin\_width}_b$ equals the paper's quoted total cross-section (absolute) or $\approx 1$ (normalized). A factor-of-two gap is almost always a units error (pb vs fb).
- **Bin contiguity** — `bins[i].bin_high == bins[i+1].bin_low` for all $i$; gaps/overlaps are extraction errors.
- **Normalization consistency** — for normalized distributions, luminosity-derived uncertainties are absent or vastly reduced; a canceling source with nonzero SM-weighted sum is a missed subtlety.
- **No duplicated / missing modifiers** — the always-required set is present; every name appears once.
- **Percentage range** — every `values_percent` is $\ge 0$ and typically $< 100$; values $>100$ usually mean an absolute-vs-percentage encoding error.

Failing any of these is a HARD STOP — fix before producing the report, do not flag and proceed.

## Failure modes worth watching

- **Wrong observable extracted** — the Step 1 omission; a complete loss discovered only downstream. Confirm before retrieving.
- **Misclassified normalization** — a normalized table treated as absolute (or vice versa), which silently mis-handles luminosity and the SM-template k-factor in `sf-sm-template`. Caught by Step 2's self-consistency checks.
- **$S \ne$ paper total systematic** — a source missing from the decomposition list (often a paper's "Other"/"Sum of small effects" row); the Schmal round-trip then closes on the wrong composition.
- **Inclusive breakdown applied to a tail bin** — jet/b-tag composition is region-dependent; flag tail bins where an inclusive-region breakdown under-represents the real growth.
- **Vague `source` pointer** — "from the paper" / "standard value" fails reviewer traceability; every modifier needs a specific table/HEPData/figure pointer.
- **Naming deferred downstream** — a non-canonical modifier name that reaches `sf-datacard` forces a re-extraction; resolve names in Step 3.

## Document

Before this phase is complete, update `/output/documentation/extraction/` per `rules/sf-documentation.md` and the `sf-document` skill: `raw/` holds the original downloaded data (HEPData tarball, tables) untouched; `processed/` references the canonical extraction report (single source, not a copy); `code/` holds every extraction/digitization script that produced a kept value; and `extraction.md` logs every uncertainty **choice** and the **source** of every included uncertainty term. Extraction is all local, but the adoption gate still binds — a `values_percent` or digitized number that reaches the report must trace to a saved, re-runnable script. The phase is not done until this bucket is current.
